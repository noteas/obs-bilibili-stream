# SRT 线路：只展示不驱动；私有 RTMP-over-SRT 输出先逆向再实现

**状态**：采纳（2026-11-27）；实现前置 U-SRT 未解除

## 背景

服务端 `protocols[]` 会给出 `protocol="srt"` 的线路，地址 scheme 为 `rtmpsrt://`。E-23 定案：

- 官方客户端把它交给外挂 `bvc_srt_output`（`plugins\bvc-srt-stream.dll`），语义是
  **RTMP/FLV over SRT**（同族 `bmtsrt` = BMT over SRT，SRT 仅作链路层）；不是 MPEG-TS over SRT。
- 标准 SRT（OBS 原生 SRT/FFmpeg mpegts）与它**不互通**。
- OBS 上游把 `rtmpsrt://` 静默降级成 `rtmp://host:1935`（TCP RTMP），所以"OBS 能直接填"
  并不等于支持 SRT（§4.6）。
- 没有任何公开 OBS 插件支持该私有封装；唯一开源参考是 FFmpeg 的 `rtmpsrt` 实验补丁
  （2021、从未合并、基于 n4.1）。官方 DLL 闭源、Windows PE、不可分发。

## 决策

1. **现阶段维持 ADR-0005**：`srt`/`rtmpsrt` 线路只原样展示（地址+推流码可复制），
   插件不驱动任何输出、不改 OBS 配置，也不把 `rtmpsrt://` 改写成 `rtmp://`
   （OBS 行为等价，改写无收益且偏离"原样展示"）。
2. **若实现 SRT 输出，必须是自研/集成的 RTMP-over-SRT 输出**：
   不复用 OBS 原生 SRT（载荷是 MPEG-TS），不复用 `bvc-srt-stream.dll`（闭源/平台不符）。
   候选轮子 = libsrt + FFmpeg `rtmpsrt` 参考实现 + OBS output/service 插件模板（E-23 §7）。
3. **实现前必须先逆向 `bvc-srt-stream.dll`（U-SRT）**，钉死：UDP 端口、SRT streamid 构造、
   载荷（完整 RTMP 握手/chunk vs 裸 FLV tag）、鉴权（`code` 如何进入 streamid/publish）、
   重连与统计。清单见 E-23 §6；未钉死前不得动码。
4. **实现形态另立 ADR**：`obs_output` 插件（service+output，用户可在直播设置里选）与
   "本地 relay"（OBS 推 localhost，插件/子进程转发）是两种不同架构，待 U-SRT 解除后决策。
   在此之前不新增 libsrt 依赖、不扩媒体面。

## 后果

- 未实现前功能无损：OBS 用户继续用同一入口的 TCP RTMP（`rtmpsrt://` 或 `rtmp://` 均可）。
- 真要做时，插件会从"信令面代理"扩展到"媒体面输出"：新增 libsrt 依赖、输出生命周期、
  编码器绑定、重连状态机与跨平台构建，维护成本显著上升；且私有封装随时可能随直播姬改版。
- 协议细节未确认前，任何"直接用标准 SRT"的方案都不可行。
