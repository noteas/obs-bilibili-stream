# 备流、选协议、断流恢复统一收敛为切换式服务改写

OBS 单实例只有一路流输出,同时双推需双编码器(CPU 翻倍),架构上不可行。决定:~~全仓库的"换推流地址"只有一个实现 —— **服务改写**(把推流目标落到 OBS 服务配置,见 ADR-0001):备流(`backup_stream=1` 请求 + 存 `protocols_backup[]` + 控制台「切到备流」)、多协议选择(`protocols[]` 下拉,rtmp→rtmp_custom、srt→OBS 内置 SRT 服务,未知协议忽略并记日志)、断流恢复(取回地址后同样走本管线)都是它的调用方~~(2026-11-25 实现路径已由 ADR-0005 推翻:全部线路只读展示,插件不改写 OBS 配置);切换完成后由用户重新点推流,永不自动重推、永不双推。官方的联播(multi_screen_*)、ARTC/WHIP(仅留协议映射位)、连麦明确不做。

> **2026-11-25 修订(ADR-0005)**:"统一收敛为服务改写"的实现路径被推翻(插件不写 OBS 配置)。仍然有效的结论:单输出、不做双推/联播/连麦;备流与多协议都只作为"线路数据"展示,由用户自行切换。

> **2026-11-26 语义更正(用户澄清)**:官方的"备流"是**主备双通道**——`backup_stream=1` 下发的是第二条独立推流通道(自己的地址+推流码),可与主流同时推,主流失效时 CDN 侧自动切到备流;同一 stream key 的第二次连接会被拒。本 ADR 的"不做同时双推"仅指**插件自身**不驱动第二路推流(单 OBS 输出);插件现在的角色=把备流通道的数据一并展示,由用户决定如何同时推。
