# 插件不改写 OBS 配置:线路全量展示,用户手动填写

**状态**: 采纳(2026-11-25),**推翻 ADR-0001 的"写回服务"条款**,并修订 ADR-0004 的落地方式。

## 背景

ADR-0001 定的是"开播与推流两条轴,插件把地址半自动写进 OBS 服务配置"。实网联调后用户明确要求:**不主动改 OBS 配置**。现实理由:

1. 写 `Service.settings` 会覆盖用户正在使用的推流配置(编码/多路/协议全被换成 `rtmp_custom`),副作用大于收益;
2. 官方给的不是一条地址,而是 `protocols[]`+`protocols_backup[]` 多协议多提供方(实网 2026-11-25:`bmtsrt,bmt,srt,srt,rtmp,rtmp,srt,rtmp`),"选哪条"本质是用户偏好,插件选就是替用户做决定;
3. 写回链引入过一次 SIGABRT(obs_data_get_json 误 free),维护成本与风险都在插件侧;
4. 插件承担的职责越少,越接近"信令面代理"的定位。

## 决策

- **插件不再调用** `obs_frontend_set_streaming_service` / `obs_frontend_save_streaming_service`,不改 OBS profile 的 `Service` 配置。
- 开播/找回所得的**全部线路原样落库**(`Config::stream_targets`:protocol/provider/addr/key/backup),控制台以可编辑只读文本行逐条展示,地址与推流码均可选中复制。
- 用户自行在 OBS「设置→直播」选择服务类型并填写;插件不解释、不改写、不排序,仅展示官方返回值。
- 仍然保留:插件**从不**调用 `obs_frontend_streaming_start`;"开始直播"永远是用户点。
- 因"换地址"不再是插件动作,原先挂在写回管线上的三个功能改为纯展示:协议选择(ADR-0004 的多协议下拉)、备流"切到备流"按钮、断流恢复。

## 后果

- 多一步手工复制;换来 OBS 配置不被覆盖、协议选择权在用户。
- 备流的"切换式"语义不再由插件执行(ADR-0004 保留"不做双推"的结论,删除其"经服务改写落地"的实现路径)。
- 线路表随场次作废:停播/服务端结束场次时清空(密钥每场新生成)。
