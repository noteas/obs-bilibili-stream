# 插件不改写 OBS 配置：线路全量展示，用户手动填写

**状态**：采纳（2026-11-25）

## 背景

官方开播响应给的不是一条地址，而是 `protocols[]` + `protocols_backup[]` 的多协议、多提供方线路（实网 2026-11-25 观测：`bmtsrt,bmt,srt,srt,rtmp,rtmp,srt,rtmp`）。“选哪条”本质是用户偏好；插件替用户写 `Service.settings` 会覆盖用户正在使用的推流配置（编码/多路/协议全被换成 `rtmp_custom`），副作用大于收益。插件定位为信令面代理，承担的职责越少越稳。

## 决策

- 插件**不调用** `obs_frontend_set_streaming_service` / `obs_frontend_save_streaming_service`，不改 OBS profile 的 `Service` 配置。
- 开播/找回所得的**全部线路原样落库**（`Config::stream_targets`：protocol/provider/addr/key/backup），控制台以只读文本行逐条展示，地址与推流码均可选中复制。
- 用户自行在 OBS「设置→直播」选择服务类型并填写；插件不解释、不改写、不排序，仅展示官方返回值。
- 插件**从不**调用 `obs_frontend_streaming_start`；“开始直播”永远是用户点。
- 协议选择、备流、断流恢复都只展示线路，不触发任何 OBS 配置写入或自动重推。

> **2026-11-27 修订（ADR-0007）**：为接入私有 SRT 输出，插件允许写 **rtmp-services 的用户级
> 服务目录** `plugin_config/rtmp-services/services.json`（在 OBS 原生服务表上合并一条
> 「B站私有 SRT」，协议 `bvc_srt`）。这属于扩展 OBS 的服务目录，不写用户已选的
> Service/编码/输出/多路配置，也不调用 `obs_frontend_set_streaming_service`/`save_streaming_service`；
> 选服务、填推流码、点开始直播仍全部由用户完成。除此之外本文其余约束不变。

## 后果

- 多一步手工复制；换来 OBS 配置不被覆盖、协议选择权在用户。
- 线路表随场次作废：停播/服务端结束场次时清空（密钥每场新生成）。
- 备流是主备双通道，插件只展示其线路数据；是否自行配置第二路输出由用户决定。
